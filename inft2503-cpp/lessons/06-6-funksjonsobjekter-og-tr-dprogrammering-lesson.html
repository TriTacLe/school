Funksjonsobjekter

Vi har før sett på bruken av anonyme funksjoner som ble definert ved hjelp av lambda uttrykk ([](){}):

#include <iostream>

using namespace std;

int main() {
  auto add = [](int a, int b) {
    return a + b;
  };
  cout << add(2, 2) << endl;
}

Vi kan også skrive dette slik:

#include <functional>
#include <iostream>

using namespace std;

int main() {
  function<int(int, int)> add = [](int a, int b) {
    return a + b;
  };
  cout << add(2, 2) << endl;
}

Siden funksjoner er minneområder der instruksjonene til funksjonen ligger, kan en lagre pekerne til starten av disse minneområdet i funksjonsobjekter. I tilfellet over heter dette objektet add som er av typen std::function. Dette kan vi utnytte for å plassere kode, som ikke hører hjemme i klassen, utenfor klassen.

I øving 5 for eksempel, blir std::cout brukt til å skrive ut om et sjakktrekk er gyldig eller ikke. Bruken av std::cout var dermed hardkodet i ChessBoard klassen. Dersom vi senere vil lage et grafisk grensesnitt mot ChessBoard klassen, blir det vanskelig gjenbruke denne klassen. Vi kan i stedet legge til std::function objekter i ChessBoard som en bruker i de tilfellene en kanskje vil utføre ekstra operasjoner fra en annen plass i kildekoden, altså utenfor ChessBoard klassen. For eksempel slik (se example1.cpp):

Om vi kaller et std::function objekt som ikke er definert, får vi std::bad_function_call exception. Dette er grunnen til at vi for eksempel skriver: if (on_piece_move) on_piece_move(*piece, from, to);. Det er ikke gitt at programmet som bruker ChessBoard klassen har definert on_piece_move funksjonsobjektet. Dette kan for eksempel være tilfellet når en lager en test av klassen.

Du lurer kanskje på hva vitsen er i å legge til slike funksjonsobjekter? Det fører til mer skriving, men gevinsten blir synlig når en lager et større program. Et eksempel kan være at vi tenker at vi har to klasser; en klasse ChessBoardDraw som tar seg av tegning og animasjoner relatert til sjakkbrettet, og en klasse ChessBoardSound som tar seg av lyder i sjakkspillet. Vi kan da definere for eksempel on_piece_move på følgende måte:

ChessBoard board;
ChessBoardDraw draw(board.squares); // En tegne klasse må ha tilgang til brikkene på de ulike rutene
ChessBoardSound sound;

board.on_piece_move = [&draw, &sound](const ChessBoard::Piece &piece, const string &from, const string &to) {
  draw.move_piece(piece, from, to);
  sound.move_piece(piece); // Kanskje vi vil ha ulike lyder for flytting av de ulike brikkene
};

...

Vi har dermed en sjakkbrett-klasse som er fullstendig uavhengig av både tegning og lyder, og når noen ser på kildekoden så er det ingen tvil om hvor tegningen finner sted. I tillegg, om vi vil lage tester, vil vi ikke lage tester for tegning eller lyder (normalt sett), men å lage tester for ChessBoard klassen sammen med de ulike Piece-subklassene gir mening.

Til slutt kan det sies at kildekoden til Øving 5, med forbedringene skissert over, likevel har forbedringspotensiale, men vi lar dette ligge for å ikke komplisere eksempelet ytterligere.

Det viktigste er å forstå bruken av funksjonsobjekter som et moderne alternativ til, og som ofte er bedre enn, å lage virtuelle funksjoner som må implementeres i en subklasse. I gamle dager ville vi ha laget virtual void on_piece_move for eksempel, og vi måtte lage en subklasse av ChessBoard for å implementere denne metoden. Se for eksempel igjen på https://gitlab.com/ntnu-ifud1048/gtkmm-example/blob/master/main.cpp, der programmet er skrevet på noen få linjer. Før i tiden hadde vi laget subklasser av både Gtk::Entry og Gtk::Button for å definere hva som skal skje ved endring, aktivering og klikk. Nå står vi derimot fritt til å legge implementasjonene der vi vil, og der de måtte høre hjemme, ved hjelp av funksjonsobjekter. I tillegg, som et resultat at vi nå typisk jobber med færre klasser, er at klassestrukturen gir lettere mening for andre programmerere.

Som oppsummering, for eksempel med utgangspunkt i https://gitlab.com/ntnu-ifud1048/gtkmm-example/blob/master/main.cpp, dersom en skal lage en ny type knapp så gir det mening å subklasse Gtk::Button, men om en vil legge til funksjoner som hva som skal skje ved klikk på en vanlig knapp, bør en bruke button.signal_clicked().connect() (som tilsvarer bruken av funksjonsobjekter).

Trådprogrammering

Slik lager vi en tråd i C++:

#include <iostream>
#include <thread>

using namespace std;

int main() {
  thread a_thread([] {
    cout << "from a_thread" << endl;
  });

  cout << "from main thread" << endl;

  a_thread.join(); //Her venter til at a_thread er fullført
}
// Eksempel utskrift:
// message from main thread
// message from a_thread

For å jobbe med tråder i Linux må en fortsatt (2016) legge til -pthread i CMAKE_CXX_FLAGS i CMakeLists.txt (se CMakeLists.txt i eksempelkoden).

La oss si at vi oppretter tråden i en funksjon og vil legge til en melding til tråden:

#include <iostream>
#include <string>
#include <thread>

using namespace std;

// to demonstrate the problem, we need to move the below calls to another stack frame (away from main()):
void f() {
  string message("some message");
  thread a_thread([&message] {
    cout << "message from a_thread: " << message << endl;
  });
  a_thread.detach(); // the thread will execute independently from the rest of the program
                     // even when the thread object a_thread goes out of scope
}

int main() {
  f();

  cout << "from main thread" << endl;

  this_thread::sleep_for(50ms); // wait 50 ms before return from main()
}
// Eksempel utskrift (kjør programmet flere ganger):
// sh: line 1: 23025 Segmentation fault

Problemet her er at message kanskje blir frigjort fra minnet før a_thread fullfører. Vi kunne laget en kopi av message (av typen std::string) når vi fanger objektet i tråden (thread a_thread([message] {), men det ønsker vi som regel ikke. Alternativet er å bruke referansetelling gjennom std::shared_ptr (i stedet for å bruke std::string direkte), der en teller antall kopier av et std::shared_ptr objekt som inneholder meldingen (se example2.cpp):

#include <iostream>
#include <memory>
#include <string>
#include <thread>

using namespace std;

// to demonstrate the problem, we need to move the below calls to another stack frame (away from main()):
void f() {
  shared_ptr<string> message(new string("some message"));  // message pointer count is increased by one
  thread a_thread([message] {                              // message pointer count is increased by one
    cout << "message from a_thread: " << *message << endl;
  });                                                      // message pointer count is decreased by one
  a_thread.detach();
}                                                          // message pointer count is decreased by one

int main() {
  f();

  cout << "from main thread" << endl;

  this_thread::sleep_for(50ms); // wait 50ms before return from main()
}
// Eksempel utskrift (kjør programmet flere ganger):
// from main thread
// message from a_thread: some message

Når pekertelleren til message (som er av typen std::shared_ptr) går til 0, slettes message objektet. message inneholder en peker til et std::string objekt som ligger i heapen. Dette std::string objektet inneholder "some message", men når message slettes, blir også std::string objektet frigjort fra minnet.

I stedet for:

shared_ptr<string> message(new string("some message"));

er det ofte vanlig å skrive (som ved unique_ptr):

auto message = make_shared<string>("some message");

Mutex

Om flere tråder jobber med samme ressursene, må en passe på at de ikke endrer og leser fra variablene eller objektene samtidig:

#include <iostream>
#include <mutex>
#include <string>
#include <thread>
#include <vector>

using namespace std;

int main() {
  string message;

  vector<thread> threads;
  for (int c = 0; c < 4; ++c) {
    threads.emplace_back([c, &message] {
      message += "thread " + to_string(c) + " says hello\n";
    });
  }

  for (auto &thread : threads)
    thread.join();

  cout << message << endl;
}
// Mulig utskrift:
// malloc: *** error for object 0x7fb968600080: double free

Vi bruker da mutex'er for å låse lese/skrive tilgangen til objektene:

#include <iostream>
#include <mutex>
#include <string>
#include <thread>
#include <vector>

using namespace std;

int main() {
  string message;

  vector<thread> threads;
  for (int c = 0; c < 4; ++c) {
    threads.emplace_back([c, &message] {
      static mutex message_mutex;            // We can declare the mutex as static if it is not needed elsewhere
      lock_guard<mutex> lock(message_mutex); // The message_mutex is locked upon construction of lock, and
                                             // the mutex is unlocked when lock is destroyed at the end of scope,
                                             // including when an exception is thrown
      message += "thread " + to_string(c) + " says hello\n";
    });
  }

  for (auto &thread : threads)
    thread.join();

  cout << message;
}
// Mulig utskrift:
// thread 0 says hello
// thread 3 says hello
// thread 2 says hello
// thread 1 says hello

I stedet for å bruke message_mutex.lock() og message_mutex.unlock(), er det tryggere å utnytte seg av lock_guard objekter som tar seg av låsing og opplåsing av mutex'er automatisk. En slipper da å ta hensyn til om en exception blir utløst. En annen kommentar til kildekoden over, er om bruken av static. Objekter som er deklarert som static blir kun initialisert en gang og lever til programmet avsluttes. Derimot trenger ikke et static objekt å bli initialisert før en trenger det, om en i det hele tatt trenger objektet. Dette vil variere med bruken av programmet, men uansett så garanterer C/C++ at initialisering av static objekter er trygt selv i tråder (thread safe).

Denne egenskapen til static blir brukt i C++ for å lage singleton klasser (singleton klasse: det finnes maks en instanse av klassen):

class SingletonClass {
  SingletonClass() {} // Constructor is private, the static get() method must be used to get/create the instance

public:
  static SingletonClass &get() {
    static SingletonClass instance;
    return instance;
  }
};

int main() {
  SingletonClass::get(); // An instance of SingletonClass is created and returned
  SingletonClass::get(); // The already created instance is returned
}

Reference-counted singleton classes (ikke pensum)

For interesserte så kan vi også legge til singleton klasser der instansen blir slettet når den ikke lenger er i bruk:

#include <memory>
#include <mutex>

using namespace std;

class ReferenceCountedSingletonClass {
  ReferenceCountedSingletonClass() {}

public:
  ///If an instance is already in use, return cached instance, otherwise return a new instance.
  static shared_ptr<ReferenceCountedSingletonClass> get() {
    static weak_ptr<ReferenceCountedSingletonClass> cache;
    static mutex cache_mutex;
    lock_guard<mutex> lock(cache_mutex); // Needed to make this get() method thread safe
    auto instance = cache.lock();
    if (!instance)
      cache = instance = shared_ptr<ReferenceCountedSingletonClass>(new ReferenceCountedSingletonClass());
    return instance;
  }
};

int main() {
  {
    auto s1 = ReferenceCountedSingletonClass::get(); // Instance is created
    auto s2 = ReferenceCountedSingletonClass::get(); // Already created instance is returned
  }                                                  // instance is destroyed
  auto s3 = ReferenceCountedSingletonClass::get();   // Instance is created
}

Denne teknikken er brukt for eksempel i https://gitlab.com/ntnu-tdat3023/sfml-modern-opengl-example for oppretting av grafikkort shadere, som blir slettet når de ikke lenger trengs for å frigjøre ressurser på grafikkortet.

Asynkron tjeneste

Av og til kan det være ønskelig å sende oppgaver til en asynkron tjeneste i stedet for å jobbe med tråder manuelt. Vi kan også velge hvor mange tråder som skal bli brukt til å utføre oppgavene våre, og i noen tilfeller vil vi faktisk at oppgavene skal kun bli kjørt i en tråd. Boost.Asio er et bibliotek som gjør dette mulig. Nedenfor lager vi en asynkron tjeneste med 4 tråder eller 4 arbeidere (workers) (se example3.cpp):

#include <boost/asio.hpp>
#include <iostream>
#include <thread>
#include <vector>

using namespace std;

class Workers {
public:
  /// Provides asynchronous service
  boost::asio::io_service service;

private:
  /// See Workers-constructor. Makes service.run() wait for tasks through service.post
  boost::asio::io_service::work work;
  vector<thread> threads;

public:
  Workers(size_t number_of_threads) : work(service) {
    for (size_t c = 0; c < number_of_threads; ++c) {
      threads.emplace_back([this] {
        service.run(); // Wait for, and execute, tasks until service.stop() is called
      });
    }
  }

  /// Stop the workers
  void stop() {
    service.stop();
    // Wait for the threads to finish
    for (auto &thread : threads) {
      thread.join();
    }
  }
};

int main() {
  Workers workers(4); // Use 4 workers (worker threads)

  cout << "Press enter to exit" << endl;

  // Give tasks to the workers:
  workers.service.post([&workers] {
    cout << "task A is being performed by a worker" << endl;

    // One can post new tasks inside a post:
    workers.service.post([] {
      cout << "task B is being performed by a worker" << endl;
    });
  });
  workers.service.post([] {
    cout << "task C is being performed by a worker" << endl;
  });

  string line;
  getline(cin, line); // stop when enter is pressed
  workers.stop();
}
// Mulig utskrift (ikke alltid like ryddig!):
// Press enter to exit
// task A is being performed by a worker
// task C is being performed by a worker
// task B is being performed by a worker

Legg spesielt merke til at post-kallene er asynkrone, altså at de returnerer umiddelbart. Utskriften blir heller ikke alltid like ryddig (kjør eksempelet flere ganger), siden utskriften blir utført parallelt i de ulike trådene.

Vi kan til og med snu det hele på hodet, og bruke Workers klassen over til å utføre funksjoner, som er kalt fra ulike tråder, sekvensielt i en tråd (se example4.cpp):

int main() {
  Workers worker(1); // Use only 1 worker (1 worker thread)

  cout << "Press enter to exit" << endl;

  std::vector<thread> threads;
  for (size_t c = 0; c < 4; ++c) {
    threads.emplace_back([&worker, c] {
      // Do some heavy work here
      this_thread::sleep_for(1s); // Simulate heavy work taking 1 second

      // Send the result to worker
      auto result = make_shared<string>("some result from thread " + to_string(c));
      worker.service.post([result] {
        // This function is guaranteed to run sequentially (1 thread)
        // because worker is running only one worker thread
        cout << "The result was: " << *result << endl;
      });
    });
  }

  string line;
  getline(cin, line); // stop when enter is pressed
  worker.stop();

  for (auto &thread : threads)
    thread.join();
}
// Mulig utskrift:
// Press enter to exit
// The result was: some result from thread 0
// The result was: some result from thread 2
// The result was: some result from thread 1
// The result was: some result from thread 3

Det eneste som kan endre seg i utskriften av example4.cpp, er hvilken tråd nummer resultatet kom fra. Og dette uten å bruke mutex låsing.

Mange biblioteker utnytter seg av å utføre visse oppgaver i en tråd, i en hendelses løkke (event loop). Node.js, som bruker libuv (C-bibliotek) gjør det slik, og de fleste GUI bibliotekene lar deg programmere i en tråd. Dette for å unngå alle problemene som kan oppstå ved å jobbe med flere tråder. Noen tyngre operasjoner blir derimot utført i worker threads, for eksempel filbehandling og kommunikasjon over nettverk, men resultatet blir sendt tilbake til hendelses løkken som kjører i en tråd (se example5.cpp):

int main() {
  Workers event_loop(1);
  Workers worker_threads(5);

  cout << "Press enter to exit" << endl;

  event_loop.service.post([&event_loop, &worker_threads] {
    // Event loop starts here (think of this as the main() of the event loop)

    // Do some heavy work in a worker_thread
    cout << "Starting heavy work from a worker thread here" << endl;
    worker_threads.service.post([&event_loop] {
      // Simulate heavy work taking 2 seconds
      this_thread::sleep_for(2s);
      // When done, send result to event loop:
      auto result = make_shared<string>("Some result");
      event_loop.service.post([result] {
        // Do something with the result in the event loop
        cout << "Result from a worker thread: " << *result << endl;
      });
    });

    // Do some heavy work in another worker_thread
    cout << "Starting heavy work from another worker thread here" << endl;
    worker_threads.service.post([&event_loop] {
      // Simulate heavy work taking 1 second
      this_thread::sleep_for(1s);
      // When done, send result to event loop:
      auto result = make_shared<string>("Some another result");
      event_loop.service.post([result] {
        // Do something with the result in the event loop
        cout << "Result from another worker thread: " << *result << endl;
      });
    });
  });

  string line;
  getline(cin, line); // stop when enter is pressed
  worker_threads.stop();
  event_loop.stop();
}
// Output
// Starting heavy work from a worker thread here
// Starting heavy work from another worker thread here
// Result from another worker thread: Some another result
// Result from a worker thread: Some result

Eksempelet over viser hvordan Node.js i bunn og grunn fungerer. Vi kunne faktisk fortsett og implementert en ny Node.js kjerne i C++ med Boost.Asio.

I stedet skal vi se på hvordan vi kan relativt enkelt lage en svært effektiv nettverksapplikasjon som kjører i en tråd (ofte kjappere enn å bruke flere tråder), men likevel støtter mer enn 1 samtidige oppkoblinger (se example6.cpp):

#include <boost/asio.hpp>
#include <iostream>

using namespace std;
using namespace boost::asio::ip;

class EchoServer {
private:
  class Connection {
  public:
    tcp::socket socket;
    Connection(boost::asio::io_service &io_service) : socket(io_service) {}
  };

  boost::asio::io_service io_service;

  tcp::endpoint endpoint;
  tcp::acceptor acceptor;

  void handle_request(shared_ptr<Connection> connection) {
    auto read_buffer = make_shared<boost::asio::streambuf>();
    // Read from client until newline ("\r\n")
    async_read_until(connection->socket, *read_buffer, "\r\n",
                     [this, connection, read_buffer](const boost::system::error_code &ec, size_t) {
      // If not error:
      if (!ec) {
        // Retrieve message from client as string:
        istream read_stream(read_buffer.get());
        std::string message;
        getline(read_stream, message);
        message.pop_back(); // Remove "\r" at the end of message

        // Close connection when "exit" is retrieved from client
        if (message == "exit")
          return;

        cout << "Message from a connected client: " << message << endl;

        auto write_buffer = make_shared<boost::asio::streambuf>();
        ostream write_stream(write_buffer.get());

        // Add message to be written to client:
        write_stream << message << "\r\n";

        // Write to client
        async_write(connection->socket, *write_buffer,
                    [this, connection, write_buffer](const boost::system::error_code &ec, size_t) {
          // If not error:
          if (!ec)
            handle_request(connection);
        });
      }
    });
  }

  void accept() {
    // The (client) connection is added to the lambda parameter and handle_request
    // in order to keep the object alive for as long as it is needed.
    auto connection = make_shared<Connection>(io_service);

    // Accepts a new (client) connection. On connection, immediately start accepting a new connection
    acceptor.async_accept(connection->socket, [this, connection](const boost::system::error_code &ec) {
      accept();
      // If not error:
      if (!ec) {
        handle_request(connection);
      }
    });
  }

public:
  EchoServer() : endpoint(tcp::v4(), 8080), acceptor(io_service, endpoint) {}

  void start() {
    accept();

    io_service.run();
  }
};

int main() {
  EchoServer echo_server;

  cout << "Starting echo server" << endl
       << "Connect in a terminal with: telnet localhost 8080. Type 'exit' to end connection." << endl;

  echo_server.start();
}

I eksempelet over, så returnerer async_... funksjonene umiddelbart, og lambda parameterne (de anonyme funksjonene) blir kjørt når de ulike async funksjonene har fullført handlingene sine. Alle de ulike shared_ptr objektene (connection, read_buffer og write_buffer) blir kopiert for å holde de ulike ressursene i live til de ikke trengs lenger. Litt nytt er det også med strømmer og buffere, men bufferne (boost::asio::streambuf objektene) inneholder data'en som enten er mottatt eller skal bli sendt, mens strømmene (istream og ostream objektene) lar oss lese fra og skrive til bufferne. Det kan også se ut som at vi har rekursive funksjonskall, men dette er trygt siden de asynkrone funksjonene returnerer umiddelbart og scopet av funksjonene som blir kalt på nytt (rekursivt) avsluttes og stack frame'en blir dermed frigjort. Vi står også fritt til å opprette tråder om vi trenger å utføre tyngre operasjoner, men da må vi passe på å ta vare på connection objektet gjennom å kopiere dette objektet videre som vist over.
