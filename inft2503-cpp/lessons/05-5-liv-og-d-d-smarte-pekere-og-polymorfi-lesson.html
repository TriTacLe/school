1. Liv og død

I C++ lever variabler og objekter på stacken i et scope:

int main() {
  {            // nytt scope her
    int a = 2; // a blir opprettet i minnet
  }            // a blir slettet fra minnet når scopet blir avsluttet
}

Hver gang du bruker { opprettes et nytt scope. Vi kan i tillegg definere hva som skal skje når et objekt blir slettet fra minnet ved hjelp av destruktører:

#include <iostream>

using namespace std;

class A {
public:
  A() {
    cout << "Objektet blir opprettet" << endl;
  }
  ~A() {
    cout << "Objektet blir slettet" << endl;
  }
};

int main() {
  {
    A a;
  }
  cout << "Scopet er avsluttet" << endl;
}
// Utskrift:
// Objektet blir opprettet
// Objektet blir slettet
// Scopet er avsluttet

Noen klasser er mer avanserte og har data lagret i det såkalte frie lageret, men både objektet (som lagres på stacken) og innholdet til objektet (som kan være lagret i det frie lageret eller "heapen") blir frigjort når et scope blir avsluttet:

#include<string>

using namespace std;

int main() {
  {                    // nytt scope her
    string a = "test"; // a blir opprettet i stacken, mens ”test” er lagret i det frie lageret
  }                    // objektet a og innholdet til a blir slettet fra minnet når scopet blir avsluttet
}

Typisk er data med ikke-fastsatt størrelse lagret på heapen. Hovedgrunnen til dette er at lagringsplassen til stacken er mye mindre enn lagringsplassen til heapen. Når vi bruker ferdige klasser som string og vector så slipper vi å forholde oss til om innholdet er lagret i det frie lageret. Men i andre tilfeller må vi tenke på det.

Det frie lageret ("heapen")

I Java opprettes alle objekter med new, og de havner dermed på heapen.

Også i C++ bruker vi new for å lagre objekter i det dynamiske minnet, som vi kaller det frie lageret ("the free store") eller "heapen".

I motsetning til "vanlige" (stakk-)variabler, har en variabel i det frie lageret ikke noe navn. I stedet lar vi en peker peke til den. Operatoren new brukes til dette, og vi må angi hvilken datatype variabelen skal ha:

#include <iostream>

using namespace std;

class A {
public:
  A() {
    cout << "Objektet blir opprettet" << endl;
  }
  ~A() {
    cout << "Objektet blir slettet" << endl;
  }
};

int main() {
  {
    A *a = new A(); // Det opprettes et anonymt objekt på heapen som a peker til
  }
  cout << "Scopet er avsluttet" << endl;
}
// Utskrift:
// Objektet blir opprettet
// Scopet er avsluttet

Hvorfor blir ikke destruktøren til det anonyme objektet som a peker på kalt? Svaret er at variabler eller objekter som er lagret på heapen, blir ikke automatisk slettet når pekeren går ut av scopet! En må da bruke operatoren delete for å frigjøre plassen igjen:

#include <iostream>

using namespace std;

class A {
public:
  A() {
    cout << "Objektet blir opprettet" << endl;
  }
  ~A() {
    cout << "Objektet blir slettet" << endl;
  }
};

int main() {
  {
    A *a = new A();  // Det opprettes et anonymt objekt på heapen som a peker til
    delete a;
  }
  cout << "Scopet er avsluttet" << endl;
}
// Utskrift:
// Objektet blir opprettet
// Objektet blir slettet
// Scopet er avsluttet

unique_ptr

Det er lett å glemme å slette et objekt på heapen, og der er tilfeller det kan være vanskelig å vite når et slikt objekt bør slettes. Heldigvis har nyere C++ løst dette med smarte pekere. I denne leksjonen tar vi for oss en av disse smarte pekerene, unique_ptr:

#include <iostream>
#include <memory>   // For unique_ptr

using namespace std;

class A {
public:
  A() {
    cout << "Objektet blir opprettet" << endl;
  }
  ~A() {
    cout << "Objektet blir slettet" << endl;
  }
};

int main() {
  {
    unique_ptr<A> a(new A()); // Et objekt opprettes på heapen, som a peker til
                              // Når a slettes, frigjøres også det anonyme objektet
  }
  cout << "Scopet er avsluttet" << endl;
}
// Utskrift:
// Objektet blir opprettet
// Objektet blir slettet
// Scopet er avsluttet

Ved hjelp av smarte pekere kan vi dermed programmere tryggere uten å være redd for at vi glemmer å slette objekter lagret i det frie lageret. Vi skal i en senere leksjon se på bruk av shared_ptr som gir oss referansetelling i C++ (en form for "garbage collection"). shared_ptr er mye brukt i tråd programmering, der det er vanskelig å vite på forhånd når et objekt skal slettes.

Referanse telling er derimot mer ressurskrevende og en skal ikke bruke det når det ikke trengs. unique_ptr koster ikke noe ekstra å bruke, men en får da ikke lov til å kopiere unique_ptr objekter (da trengs referansetelling). Derimot kan vi flytte på innholdet med move operatoren om vi trenger det:

#include <iostream>
#include <memory>

using namespace std;

int main() {
  unique_ptr<int> p1(new int(2)); // p1 peker til tallet 2 lagret på heapen
  unique_ptr<int> p2;             // p2 peker til ingenting (inneholder nullptr)

  //p2 = p1                       // ikke lov med unique_ptr
  p2 = move(p1);                  // flytter pekeren i p1 til p2
                                  // p1 inneholder nå nullptr

  if (!p1)
    cout << "p1 inneholder nullptr" << endl;

  if (p2) {
    // get() returnerer pekeren unique_ptr-objektet inneholder:
    cout << "p2 har addressen " << p2.get() << " som inneholder tallet " << *p2 << endl;
  }
}
// Eksempel utskrift:
// p1 inneholder nullptr
// p2 har addressen 0xd59c20 som inneholder tallet 2

I eksempelet over så er det også vist (feks: if (p2)) hvordan en enkelt kan sjekke om en smart peker inneholder en gyldig adresse eller ikke (nullptr).

En kan også slette objektet en unique_ptr peker til ved å skrive for eksempel p2 = nullptr. I tillegg kan en lage et nytt objekt som unique_ptr peker til: p1 = unique_ptr<int>(new int(2)), og da vil objektet som p1 eventuelt allerede peker til bli slettet. En kan også bruke make_unique for å enklere opprette unique_ptr-objekter. Noen eksempler:

#include <iostream>
#include <memory>

using namespace std;

class A {
public:
  A() {
    cout << "Objektet blir opprettet" << endl;
  }
  ~A() {
    cout << "Objektet blir slettet" << endl;
  }
};

int main() {
  {
    auto a = make_unique<A>(); // Dette er det samme som å skrive:
                               // unique_ptr<A> a(new A());
    a = make_unique<A>();
    a = nullptr;
    a = make_unique<A>();
  }
  cout << "Scopet er avsluttet" << endl;
}
// Mulig utskrift:
// Objektet blir opprettet
// Objektet blir opprettet
// Objektet blir slettet
// Objektet blir slettet
// Objektet blir opprettet
// Objektet blir slettet
// Scopet er avsluttet

Legg merke til at destruktøren til A blir kalt like mange ganger som konstruktøren, noe som gjør det veldig trygt å jobbe med smarte pekere. I tillegg, gir vi ofte pekere navn som representerer objektene pekerne peker til, for eksempel a i stedet for en_objekt_peker.

Parametrene til make_unique er konstruktør parametrene til klassen, for eksempel kan vi skrive: auto string=make_unique<string>("tekst");.

Viktig: vi bruker smarte pekere kun når vi trenger det. Har vi muligheten til å jobbe med objekter på stacken, så gjør vi det i stedet for å lage smarte pekere. I neste kapittel, skal vi se på et av disse tilfellene der vi er nødt til å jobbe med pekere i stedet for objekter direkte.

2. Polymorfi

Polymorfi gjør det mulig å håndtere objekter med felles basisklasse under ett. Det enkelte objektet vet selv hvordan det skal reagere på en felles melding.

For å kunne håndtere slike objekter av ulik type under ett, må vi bruke pekere.

Viktig: en må passe på å ikke misbruke polymorfi. Bruk polymorfi kun når det er nødvendig! For eksempel, en trenger aldri å bruke polymorfi for å ta i bruk funksjoner i standard biblioteket til C++. Dette er et veldig bevisst valg fra ISO komitéen.

Pekere til objekter i et arvehierarki

En peker til en basisklasse kan settes til å peke til et objekt av en klasse på lavere nivå. Det omvendte er ikke tilfelle. Som eksempel bruker vi klassene fra leksjon 3:


Klassen Material representerer en generalisering av klassene Covering, Paint og Wallpaper

Gitt:

Material *material_pointer;
Covering *covering_pointer;
Material material(”SuperDuper”, 200);
Covering covering(”Dux”, 300, 5);

Kan vi skrive:

material_pointer = &material;  // ok, selvfølgelig
material_pointer = &covering;  // også ok
covering_pointer = &covering   // ok

Men vi kan ikke skrive:

covering_pointer = &material;  // ikke ok

Hvorfor er det slik? Husk at Covering er en spesialisering av Material. Klassen Covering har derfor gjerne flere medlemsfunksjoner enn Material. Vi kan gjøre ting med et Covering-objekt som vi ikke kan gjøre med et Material-objekt. Det er derfor naturlig at kompilatoren nekter oss å sette en Covering-peker til å peke til et Material-objekt. Det omvendte innebærer imidlertid ingen risiko. Alt vi kan gjøre med Material-objekter kan vi også gjøre med Covering-objekter.

Å håndtere objekter av subklasser under ett

Studer og kjør følgende eksempel som lager og bruker klassene Material, Covering, Paint og Wallpaper (koden finner dere i example1.cpp).

//
// example1.cpp
//
#include <iostream>
#include <string>

using namespace std;

class Material {
public:
  string name;
  double price; // per unit

  Material(const string &name_, double price_) : name(name_), price(price_) {}

  void print() const {
    cout << "Navn: " << name << endl
         << "Pris: " << price << endl;
  };
};

class Covering : public Material {
public:
  double width; // I meter.

  // Prisen er per meter belegg (i lengden)
  Covering(const string &name, double price, double width_)
      : Material(name, price), width(width_) {}

  void print() const {
    Material::print();
    cout << "For belegg" << endl
         << "Bredde: " << width << endl;
  }
};

class Wallpaper : public Material {
public:
  double length; // i meter per rull
  double width;  // i meter per rull

  // Prisen er per rull
  Wallpaper(const string &name, double price, double length_, double width_)
      : Material(name, price), length(length_), width(width_) {}

  void print() const {
    Material::print();
    cout << "For tapet" << endl
         << "Bredde av rull: " << width << endl
         << "Lengde av rull: " << length << endl;
  }
};

class Paint : public Material {
public:
  int coatings;         // Antall strøk
  double liters_per_m2; // Liter per kvadratmeter

  // Prisen er per liter
  Paint(const string &navn, double pris, int coatings_, double liters_per_m2_)
      : Material(navn, pris), coatings(coatings_), liters_per_m2(liters_per_m2_) {}

  void print() const {
    Material::print();
    cout << "For maling" << endl
         << "Antall strøk: " << coatings << endl
         << "liter per kvadratmeter: " << liters_per_m2 << endl;
  }
};

int main() {
  Covering covering("Super Duper Dux", 433.50, 4);
  Wallpaper wallpaper("Soldogg", 200, 12, 0.6);
  Paint paint("Extra", 125, 2, 12.0);

  // Objektet bruker sin egen print()-funksjon (ingen arv)
  covering.print();
  cout << endl;
  wallpaper.print();
  cout << endl;
  paint.print();
}

// Utskrift:
// Navn: Super Duper Dux
// Pris: 433.5
// For belegg
// Bredde: 4

// Navn: Soldogg
// Pris: 200
// For tapet
// Bredde av rull: 0.6
// Lengde av rull: 12

// Navn: Extra
// Pris: 125
// For maling
// Antall strøk: 2
// liter per kvadratmeter: 12

Dette er for så vidt greit nok, men vi burde kanskje kunne vente større effekt av arv enn dette? Selv om alle subklassene har funksjonen print() så ser det ikke ut som vi klarer å utnytte fellestrekket særlig.

Nå vet vi at dersom vi lager en peker av typen Material, så kan vi sette den til å peke til objekter av subklasser til Material. La oss lage en tabell av slike pekere og sette dem til å peke til de tre objektene:

vector<Material*> materials;
materials.emplace_back(&covering);
materials.emplace_back(&wallpaper);
materials.emplace_back(&paint);

Kan vi nå håndtere disse tre objektene under ett, for eksempel slik:

for (auto &material : materials) {
  material->print(); // Samme som (*material).print()
  cout << endl;
}

Kompilatoren godtar dette. Merk at bruken av operatoren -> er en enklere måte å skrive (*material).print() på, eller med andre ord: kall metoden til objektet som material peker til.

Så får vi se hva utskriften blir:

Navn: Super Duper Dux
Pris: 433.5

Navn: Soldogg
Pris 200

Navn: Extra
Pris: 125

Hmm... vi får ikke skrevet ut det som er særskilt for hvert enkelt objekt. Den utgaven av funksjonen print() som finnes i klassen Material blir brukt for alle objektene.

Årsaken er at dette bestemmes under kompilering. Kompilatoren ser at datatypen til materials er peker til Material, og dermed blir print() i klassen Material knyttet til variabelen materials.

Det fins en annen mulighet: Vi kan la objektet (og ikke variabeldefinisjonen) bestemme hvilken utgave av print() som skal brukes. Det er sjelden forholdene er så oversiktlig som foran, derfor må dette eventuelt skje under kjøring av programmet. Det får vi til ved å erklære funksjonen som virtual, og når vi overskriver en virtuell funksjon bruker vi nøkkelordet override.

OBS

Java-programmerere: C++ krever at funksjoner er erklært virtual, for at polymorfien skal virke. Bak denne tankegangen ligger effektiviseringshensyn. Polymorfi er ressurskrevende, og bør derfor ikke brukes hvis det ikke er nødvendig. I Java virker polymorfien alltid.

Koden nedenfor (example2.cpp) viser hvordan en bruker virtual og override:

//
// example2.cpp
//
#include <iostream>
#include <string>
#include <vector>

using namespace std;

class Material {
public:
  string name;
  double price; // per unit (

  Material(const string &name_, double price_) : name(name_), price(price_) {}

  virtual void print() const {
    cout << "Navn: " << name << endl
         << "Pris: " << price << endl;
  };
};

class Covering : public Material {
public:
  double width; // i meter

  // Prisen er per meter belegg (i lengden)
  Covering(const string &name, double price, double width_)
      : Material(name, price), width(width_) {}

  void print() const override {
    Material::print();
    cout << "For belegg" << endl
         << "Bredde: " << width << endl;
  }
};

class Wallpaper : public Material {
public:
  double length; // i meter per rull
  double width;  // i meter per rull

  // Prisen er per rull
  Wallpaper(const string &name, double price, double length_, double width_)
      : Material(name, price), length(length_), width(width_) {}

  void print() const override {
    Material::print();
    cout << "For tapet" << endl
         << "Bredde av rull: " << width << endl
         << "Lengde av rull: " << length << endl;
  }
};

class Paint : public Material {
public:
  int coatings;         // Antall strøk
  double liters_per_m2; // Liter per kvadratmeter

  // Prisen er per liter
  Paint(const string &name, double price, int coatings_, double liters_per_m2_)
      : Material(name, price), coatings(coatings_), liters_per_m2(liters_per_m2_) {}

  void print() const override {
    Material::print();
    cout << "For maling" << endl
         << "Antall strøk: " << coatings << endl
         << "Liter per kvadratmeter: " << liters_per_m2 << endl;
  }
};

int main() {
  Covering covering("Super Duper Dux", 433.50, 4);
  Wallpaper wallpaper("Soldogg", 200, 12, 0.6);
  Paint paint("Extra", 125, 2, 12.0);

  vector<Material *> materials;
  materials.emplace_back(&covering);
  materials.emplace_back(&wallpaper);
  materials.emplace_back(&paint);

  for (auto &material : materials) {
    material->print();
    cout << endl;
  }
}

Merk

Anta at vi har en funksjon som er definert både i en basisklasse og i tilhørende subklasser. Vi har videre en peker med type lik basisklassen.

Vi setter pekeren til å peke til et objekt av en subklasse.

Dersom vi til dette objektet sender en melding som er laget som en virtual funksjon, vil objektets type bestemme hvilken utgave av funksjonen som blir brukt. ("Run-time binding") Dette er polymorfi. De reserverte ordene virtual og override brukes bare i erklæringen av funksjonen, ikke i implementasjonen.

Dersom funksjonen ikke er virtual, vil datatypen til pekeren bestemme hvilken utgave som blir brukt. ("Compile-time binding")

Vi kan også forenkle main() funksjonen over ved å bruke unique_ptr (se example3.cpp):

...
#include <memory>
...

int main() {
  vector<unique_ptr<Material>> materials;
  materials.emplace_back(new Covering("Super Duper Dux", 433.50, 4));
  materials.emplace_back(new Wallpaper("Soldogg", 200, 12, 0.6));
  materials.emplace_back(new Paint("Extra", 125, 2, 12));

  for (auto &material : materials) {
    material->print();
    cout << endl;
  }
}

dynamic_cast

I eksempelet over lagret vi ulike Material pekere i vektoren materials. Av og til ønsker vi å utføre en operasjon dersom en peker peker til et objekt av en spesifikk subklasse. Til dette bruker vi dynamic_cast:

...
#include <memory>
...

int main() {
  vector<unique_ptr<Material>> materials;
  materials.emplace_back(new Covering("Super Duper Dux", 433.50, 4));
  materials.emplace_back(new Wallpaper("Soldogg", 200, 12, 0.6));
  materials.emplace_back(new Paint("Extra", 125, 2, 12));

  cout << "Malinger lagret i materials vektoren:" << endl;
  for (auto &material : materials) {
    if (dynamic_cast<Paint*>(material.get()))
      material->print();
  }
}
// Utskrift:
// Malinger lagret i materials vektoren:
// Navn: Extra
// Pris: 125
// For maling
// Antall strøk: 2
// Ant kvm./l: 12

En kunne også ha skrevet if (auto maling=dynamic_cast<Paint*>(material.get())) og da fått pekeren (Paint*) lagret i maling:

int main() {
  vector<unique_ptr<Material>> materials;
  materials.emplace_back(new Covering("Super Duper Dux", 433.50, 4));
  materials.emplace_back(new Wallpaper("Soldogg", 200, 12, 0.6));
  materials.emplace_back(new Paint("Extra", 125, 2, 12));

  cout << "Totalt antall strøk:" << endl;
  int coatings_total = 0;
  for (auto &material : materials) {
    if (auto paint = dynamic_cast<Paint*>(material.get()))
      coatings_total += paint->coatings;
  }
  cout << coatings_total << endl;
}
// Utskrift:
// Totalt antall strøk:
// 2

Virtuelle destruktører

I eksempel3.cpp har vi også lagt til denne linjen i Material klassen: virtual ~Material() {}.

Enhver klasse har eksakt én destruktør, og i enkelte tilfeller programmerer vi den selv. Destruktørene utføres nedenfra og oppover i klassehierarkiet. Det vil si at destruktøren for en avledet klasse utføres før destruktøren for en basisklasse. Dersom vi lager destruktører i et arvehierarki selv, bør de være virtuelle. Dette sikrer at alle destruktørene blir utført når et objekt slettes. Merk deg at vi ikke selv skal programmere kall av destruktøren i basis-klassen, i motsetning til for konstruktører.

3. Rene virtuelle klasser og abstrakte klasser


Material som abstrakt klasse

Studer figuren over. Vi har tatt inn beregning av behov og pris for en bestemt flate (klassen Surface er kjent fra leksjon 3). Det vi imidlertid vet er at vi ikke kan beregne behov for et generelt material. Det har ingen mening. Ingen formler klarer det for oss.

Vi ønsker imidlertid å fortelle at det er mulig å beregne behovet for alle typer materials. Dermed kan vi håndtere disse under ett (se example4.cpp):

for (auto &material : materials) {
  cout << material->name << ": "
       << " Behov: " << material->units_needed(surface)
       << " enheter, pris: " << material->price_total(surface) << endl;
}

Vi har altså følgende situasjon:

I klassen Material skal vi kun fortelle at det er rimelig at funksjonen units_needed() eksisterer for objekter av subklasser. Men vi er ikke i stand til å sette opp noen implementasjon av denne funksjonen i klassen Material.

Dette faktum viser vi i UML ved å skrive funksjonsnavnet i kursiv. Vi sier at operasjonen er abstrakt.

Det vil ikke være mulig å lage objekter av en klasse som inneholder en abstrakt operasjon. Vi sier derfor at også klassen er abstrakt. Både klassenavn og operasjonsnavn står i kursiv i UML-diagrammet.

I C++ lager vi en abstrakt operasjon ved å erklære en virtuell funksjon som rent virtuell:

virtual double units_needed(const Surface &surface) const = 0;

Vi er nå i klassen Material. Merk at vi setter funksjonen lik 0. Denne funksjonen har ingen implementasjon, ikke en gang en tom kropp, {}, i klassen Material.

En klasse som inneholder minst én ren virtuell funksjon, blir abstrakt. Det vil ikke være mulig å lage objekter av klassen.

I subklasser implementeres denne funksjonen som vanlige virtuelle funksjoner. Dersom subklassen ikke implementerer funksjonen, vil den selv bli abstrakt.

Hva med price_total()?

Denne operasjonen er ikke abstrakt i UML-diagrammet, og den er ikke engang implementert som en virtuell funksjon. Her er det mulig å sette opp en definisjon som gjelder for alle klassene:

double Material::totalpris(const Surface &surface) const {
  return units_needed(surface) * pris;
}

Denne definisjonen tilhører klassen Material, og den vil arves til subklasser.

Merk at vi her kan bruke den virtuelle funksjonen units_needed(), selv om den ikke har implementasjon i klassen Material.
