Kort om objektorientert programmering

Det sentrale i en objektorientert modell er objektene. Et objekt er en modell av en ting som problemområdet vårt handler om. Et objekt kan modellere noe konkret som en stol, et bord, en person eller en buss, eller noe abstrakt som for eksempel et møte eller en avtale. Objekter er alltid substantiver. Vi fokuserer på ansvar. Et objekt har ansvar for å kunne en del ting om seg selv. Eksempler:

  • En bil har kunnskap om sitt eget registreringsnummer, merke og modell. Den vet hvordan den starter, hvordan den kjører og hvordan den stopper.
  • En student vet sitt eget studentnummer, sine egne karakterer, navn, fødselsdato og adresse. Han vet hvordan han skal komme seg til studiestedet, og hvordan han skal løse eksamensoppgavene.
  • Et møte vet hvor det holder til, hvem som skal delta, når det starter og når det er planlagt avsluttet. Etter en tid vet det også hvem som deltok, og når det virkelig sluttet.

Et objekt har en tilstand. Tilstanden til et objekt er "en situasjon i livet til objektet, der objektet tilfredsstiller en betingelse, gjennomfører en aktivitet eller venter på at noe skal skje". Studenten kan sitte på eksamen og vente på at oppgavene blir delt ut. I det oppgavene blir delt ut går han over i en ny tilstand.

En attributt er en navngitt egenskap med et definert verdiområde. I studenteksemplet er studentnummer og adresse attributter. Verdiene til attributtene kan for eksempel være "1234567" og "Storgt. 56". Attributtet "studentnummer" består alltid av sju sifre. Verdiområdet er dermed alle heltall på sju sifre. Attributtet "adresse" kan defineres som en tekst, eller det kan være én av en nærmere spesifisert mengde adresser.

Et objekt har en identitet. Alle virkelige objekter kan skilles fra hverandre. Det samme gjelder våre modellobjekter. Vi skiller objektet med studentnummer 1234567 fra alle andre objekter.

Et objekt har en atferd (engelsk: behaviour). Objektet er i stand til å utføre en mengde oppgaver. Åse kan endre adressen sin, og hun kan gå på forelesning. Atferden til et objekt er gitt som mengden av operasjoner som objektet kan utføre.

Innkapsling (engelsk: encapsulation) er en viktig egenskap ved objekter. Opplysninger om hvordan et objekt løser en oppgave er gjemt inne i objektet. Klientobjektet trenger ikke å vite noe om hvordan tjenerobjektet løser oppgaven, bare at den kan løses. Et klientobjekt forholder seg kun til den atferden som er definert for tjenerobjektet. Klienten kan dermed kun sende et begrenset utvalg meldinger til tjenerobjektet. Det er den som konstruerer objektet som bestemmer hvilke tjenester objektet skal tilby.

En klasse er en beskrivelse av en mengde objekter som har det til felles, at de har de samme attributtene og samme atferd.

Det er vanlig å illustrere en klasse ved hjelp av et klassediagram. Dette er en standard notasjon som er en del av Unified Modeling Language (UML). UML er uavhengig av programmeringsspråk. Figuren nedenfor viser et UML eksempel for en Bil-klasse.

Klassen string

Vi begynner med å se på en av standardklassene, nemlig string som du muligens kjenner fra andre programmeringsspråk. Denne klassen brukes til å representere et sett med tegn (strenger), og inneholder flere metoder som hjelper oss til å utføre typiske operasjoner på slike strenger. Et eksempel på en slik operasjon er å kombinere to strenger.

I programmet ditt lager du et string-objekt:

string name("Ole Pettersen");

Du overlater ansvaret for streng-behandlingen til det aktuelle string-objektet. Det programmet du skriver er en klient som benytter seg av de tjenestene dette objektet tilbyr. Dette gjør klienten ved å sende meldinger til objektet name:

size_t first_space = name.find(" ", 0);       // søker etter første mellomrom
string middle_name = "Johan ";                // lager nytt objekt med en blank bakerst
name.insert(first_space + 1, middle_name);    // setter inn mellomnavnet
cout << "Nå er navnet lik: " << name << endl; // skriver ut hele navnet

Her bruker vi konstruktøren til klassen string. Denne konstruktøren har kun ett argument. I stedet for å skrive:

string name("Petter");

kan vi da bruke tegnet = foran argumentet. (Dette er en av de reglene som ikke akkurat gjør C++ enkelt å lære, men den er altså mye brukt.) Det vil si at vi kan skrive:

string name = "Petter";

Legg kodebitene foran inn i et program og kjør. Operatorene + og += er definert for objekter av klassen string:

string first_name = "Ole";
string middle_name = "Anders";
string surname = "Jensen";
string name = first_name + " " + middle_name + " " + surname;
cout << name << endl;
name += ", Åsveien 34, 1234 Buelv";
cout << name << endl;

Klassen string tilbyr ingen funksjoner for analyse og omforming av de enkelte tegnene i strengen. For å få til for eksempel omforming til bare store/små bokstaver, å sjekke om et tegn er et siffer eller en bokstav, m.v. må vi bruke funksjonene fra <cctype> og fra <cstring>.

Vi bruker []-operatoren for å referere til et enkelt tegn i strengen. Vi kan bruke [] både på venstre og høyre side av tilordningstegnet. Merk imidlertid at dersom vi bruker [] på venstre side, så må det være satt av plass til dette tegnet. Eksempel:

text = "hallo"; // streng med lengde 5, gyldige posisjoner er 0, 1, 2, 3, 4
text[3] = 'Z';  // ok!
text[5] = 'X';  // ikke ok

Programmet nedenfor går i løkke og leser inn et ord av gangen. Ordet omformes til bare store bokstaver og skrives ut:

//
// toupper.cpp
//
#include <cctype>
#include <iostream>
#include <string>

using namespace std;

int main() {
  string word;

  cout << "Skriv ord, et på hver linje, avslutt med \"x\":" << endl;

  // Vi leser ordet inn i et string-objekt
  cin >> word;

  // Vi kan bruke sammenligningsoperatorene for å sammenligne
  // innholdet i streng-objektene. (For å sammenligne strenger
  // som er lagret i char-tabeller må vi bruke strcpy(), dersom
  // vi bruker operatorene da, vil vi sammenligne adressene, og
  // det er sjelden meningen!)
  while (word != "x" && word != "X") {
    cout << word;
    for (size_t i = 0; i < word.length(); i++) {
      word[i] = toupper(word[i]);
    }

    cout << " Omformet: " << word << endl;
    cin >> word;
  }
}

Å omforme tall til strenger og omvendt

Her benytter man samme teknikk som ved utskrift av tallet. For å kunne skrive ut en tallverdi lagret på binær form må den omformes til tekstlig form. Eksempelvis vil tallverdien 76 (datatype int) omformes til tegnene '7' og '6' (datatype char) før utskrift.

I stedet for å skrive til datafil eller kommando-vinduet, "skriver" programmet til strengvariabler i minnet. Vi bruker klassen ostringstream. Følgende funksjon tar et tall som argument og returnerer en streng som inneholder tallet på tekstform.

#include <sstream>

string to_string(int number) {
 ostringstream oss;
 oss << number;
 return oss.str();
}

Merk at vi bruker samme operator som ved vanlig utskrift. Vi kan også formatere om vi ønsker det.

Å omforme en tekst til tall

Tilsvarende kan vi bruke klassen istringstream for å lese tall fra en streng. Når en streng inneholder mer enn ett tall, må vi lese flere ganger fra istringstream-objektet. Eksempel:

#include <iostream>
#include <sstream>

using namespace std;

int main() {
  istringstream iss;
  int int_number;
  double double_number;

  iss.str("10 12.5");

  iss >> int_number;
  iss >> double_number;

  cout << "int_number: " << int_number << ", double_number: " << double_number << endl;
}

// Utskrift:
// int_number: 10, double_number: 12.5

Å programmere en enkel klasse

I dette kapitlet skal vi se på hvordan vi lager en enkel klasse. Dere vil kanskje kjenne igjen mye fra andre programmeringsspråk, spesielt oppbyggingen av klassene. Noe er likevel litt forskjellig i C++, som for eksempel syntaksen, og ordbruken av de ulike delene av klassedeklarasjonene og klasseimplementasjonene.

Vi skal lage en klasse Flate sammen med et enkelt klientprogram. Filen flateTest.cpp inneholder både klassedeklarasjonen, klasseimplementasjonen og main(). Klassedeklarasjonen fungerer på samme måte som funksjonsprototyper du kjenner fra øving 1. Den gjør klassen og dens tjenester kjent for main(). Figuren under viser sammenhengen mellom klassediagrammet og klassen.

I objektorientert programmering er det vanlig å skjule datastrukturene. Derfor deklarerer (og definerer) vi disse under det reserverte ordet private. De er dermed ikke tilgjengelig utenfor klassen. Operasjonene i klassediagrammet representerer klassens offentlig tilgjengelige tjenester, vi setter opp funksjonsprototypene under det reserverte ordet public.

Både data og funksjoner er medlemmer i klassen. Vi skiller mellom datamedlemmer og funksjonsmedlemmer.

//
// surface_test.cpp
//

#include <iostream>
#include <string>

using namespace std;

// ==> Her kommer definisjonen av klassen
class Surface {
public:
  Surface(const string &name_, double length_, double width_);
  const string &get_name() const;
  double get_length() const;
  double get_width() const;
  double get_area() const;
  double get_circumference() const;

private:
  string name; // til identifikasjon
  double length;
  double width;
};

// ==> Her kommer implementasjonen av klassen
Surface::Surface(const string &name_, double length_, double width_)
    : name(name_), length(length_), width(width_) {}

const string &Surface::get_name() const {
  return name;
}

double Surface::get_length() const {
  return length;
}

double Surface::get_width() const {
  return width;
}

double Surface::get_area() const {
  return width * length;
}

double Surface::get_circumference() const {
  return 2 * (length + width);
}

//
// Dette er et program som tester klassen Flate .
// Vi tester klassen ved å opprette et objekt av klassen.
// Deretter henter vi ut dataene fra objektet og skriver disse ut,
// slik at vi kan se at objektet virkelig inneholder
// de dataene vi puttet inn, og at det gjør sine beregninger riktig.
//

int main() {
  // Trinn 1: Lager et objekt av klassen.
  Surface floor("Torils golv", 4.8, 2.3);

  // Trinn 2: Henter ut data og får utført beregninger på objektet
  string name = floor.get_name();
  double width = floor.get_width();
  double length = floor.get_length();
  double area = floor.get_area();
  double circumference = floor.get_circumference();

  // Trinn 3: Skriver ut resultatene slik at de kan kontrolleres
  cout << "Data om golvet med navn: " << name << ":" << endl;
  cout << "Bredde: " << width << endl;
  cout << "Lengde: " << length << endl;
  cout << "Areal: " << area << endl;
  cout << "Omkrets: " << circumference << endl;
}

Før main() vises klasseimplementasjonen. Her finner vi definisjonen av alle funksjonene. Merk at vi definerer funksjoner som er inni navnerommet gitt av klassen Surface. Derfor må vi sette opp Surface:: foran funksjonsnavnene. Dermed får vi tilgang til alle data (og funksjoner) deklarert inni klassen Surface. Vi ser at vi bruker variablene name, length og width inni disse funksjonene.

Å dele opp surface_test.cpp i flere filer

Bare kort om oppdeling av kildekode i to filer. Det er vanlig at funksjonsprototyper ligger i header (.hpp) filer, mens definisjonen (implementasjonen) av funksjonene ligger et annet sted (.cpp-filer). Slik gjør vi med klasser også, vi legger deklarasjonen på en header-fil, mens definisjonen ligger på en annen fil.

I eksempelkoden til denne leksjonen er dette gjort for surface_test.cpp under katalogen "refurbishment". Vi ser at klassedeklarasjonen ligger i surface.hpp-filen, mens implementasjonen ligger i surface.cpp. For at cpp-filene skal kompilere må vi inkludere surface.hpp. En av hensiktene med dette er at klassen ikke trenger å kompileres om for hver gang. Nå er vel ikke det all verden her, men i store systemer har dette betydning.

I .hpp-filene har vi også tatt med:

#pragma once

Dette er vanlig for å unngå redeklarering dersom samme header-fil inkluderes flere ganger, direkte eller indirekte. Linjer som begynner med # er direktiver til preprossessoren.

Bruken av const

Medlemsfunksjoner som endrer/ikke endrer datainnholdet i et objekt

Ingen av funksjonene foran forandrer på datainnholdet i objektet. Derfor har de const etter seg. Dette forteller den som skal bruke funksjonene at disse kan trygt brukes uten at man risikerer at datainnholdet forandres.

Nå er kanskje ikke eksemplet foran best egnet til å vise endring av datainnhold. Et golv eller en vegg forandrer sjelden bredde og lengde. Men la oss nå tenke oss at det likevel er tilfelle. Vi ønsker å sende meldingen ”Du skal ha lengde 3.7” til flateobjektet. Det blir inn-argument til medlemsfunksjonen. I klasse-deklarasjonen ser det slik ut:

void set_length(double length);  // Merk, ikke const her!

I klientprogrammet skriver vi:

floor.set_length(3.7);

Funksjoner som endrer verdien til et datamedlem kalles gjerne sett-funksjoner.

Objekter som inn-argument

Vi skal se nærmere på inn-argumentet name_ i konstruktøren:

Surface::Surface(const string &name_, double length_, double width_)
    : name(name_), length(length_), width(width_) {}

For ordens skyld gjør vi oppmerksom på at det som nå sies ikke er spesielt for konstruktører, det gjelder også inn-argumenter i funksjoner.

Vi referanseoverfører argumentet. Vi har tidligere sett hvordan vi referanseoverfører ut-argumenter. Det er imidlertid vanlig å referanseoverføre inn-argumenter også, dersom disse er objekter. For å markere at det er inn-argumenter setter vi const foran. Da vil funksjonen ikke kunne endre på argumentet (dersom funksjonen endrer argumentet ville det jo ikke lenger være et inn-argument, men et inn-/ut-argument eller ut-argument).

Vi kunne selvfølgelig ha brukt verdioverføring:

Surface::Surface(string name_, double length_, double width_)
    : name(name_), length(length_), width(width_) {}

Imidlertid er referanseoverføring både raskere og mindre plasskrevende. Verdioverføring medfører som kjent at det lages en kopi av det aktuelle argumentet, mens en referanse bare er et annet navn på en allerede eksisterende variabel.

Objekt som returverdi

La oss se på funksjonen som returnerer en const-referanse til navn:

const string &Surface::get_name() const {
  return name;
}

Her returnerer vi en referanse til datamedlemmet. Merk at vi også her bruker const. Dette for å beskytte datamedlemmet mot klienten, slik at den ikke endrer verdien til datamedlemmet.

Vi kan selvfølgelig returnere nye objekter i stedet for referanser til eksisterende. På samme måte som ved verdioverføring av argumenter lages det en kopi av originalen. Det er denne kopien som legges i variabelen på venstre side av tilordningstegnet. Eksempel:

string Surface::get_name() const {
  return name;
}

I klientprogrammet kan det stå:

Surface surface;
string surface_name = surface.get_name();

return-setningen lager en kopi av datamedlemmet name og sender denne midlertidige kopien ut av funksjonen. I klientprogrammet blir kopien overført til objektet surface_name av kompilatoren (dette gjelder fra og med C++11 standarden). Resultatet er at kun én kopiering blir utført.

Konstruktører

En konstruktør er som kjent en medlemsfunksjon med samme navn som klassen. Vi kan lage ingen, én eller flere konstruktører i en klasse. Dersom vi lager flere konstruktører, må de skille seg fra hverandre ved at argumentlistene er forskjellige.

Dersom vi ikke lager noen konstruktør, blir det laget en standardkonstruktør. Dette er en konstruktør uten argumenter og uten innhold, den ser rett og slett slik ut:

Surface::Surface() {}

En klient bruker denne konstruktøren ved å deklarere variabelen slik:

Surface surface;

Dersom vi lager minst én konstruktør selv (for eksempel: Surface::Surface(const string &name_, double length_, double width_)), vil ikke denne standardkonstruktøren bli laget. Dersom vi da forsøker oss på deklarasjonen over, vil vi få kompileringsfeil om ikke Surface::Surface() også er definert.

Advarsel

Vi bør ikke sette vår lit til den ferdiglagde standardkonstruktøren. Den medfører at datamedlemmene får vilkårlige startverdier. Vi bør i stedet enten lage vår egen konstruktør med tom argumentliste, der vi gir datamedlemmene fornuftige startverdier, eller vi bør lage andre konstruktører som vi dermed tvinger klienten til å bruke.

En egenlaget standardkonstruktør kan for eksempel se slik ut:

Surface::Surface() {
 // name har allerede blitt initialisert til standardverdien ""
 name = "NN";
 length = 0.0;
 width = 0.0;
}

Problemet over er at noen av datamedlemmene blir initialisert med standardverdier før koden i konstruktøren blir kjørt, og deretter får datamedlemmene nye verdier i koden. Vi bør i stedet skrive følgende for å initialisere datamedlemmer:

Surface::Surface(): name("NN"), length(0.0), width(0.0) {}

C++11

I C++11 kan en initialisere datamedlemmene med konstanter i klassedeklarasjonen som vist nedenfor:

class Surface {
public:
   Surface(const string &startNavn, double startLengde, double startBredde);
   Surface() {};
   const string &get_name() const;
   double get_length() const;
   double get_width() const;
   double get_area() const;
   double get_circumference() const;

private:
   string name = "NN";  // C++11
   double length = 0.0; // C++11
   double width = 0.0;  // C++11
};

Merk at vi her har lagt til Surface() {}; slik at vi kan bruke konstruktør uten parametere. Mindre og enkle funksjonsmedlemmer blir ofte lagt under klassedeklarasjonen, derfor kan vi skrive {} på slutten av Surface().

Samarbeid mellom objekter

Figuren nedenfor viser klassediagrammet som ble presentert tidligere, men utvidet med en ekstra klasse Covering (norsk: Belegg). Et objekt av klassen Covering har ansvaret for å beregne antall meter (og pris) som skal til for å dekke en flate. For å kunne gjøre det må objektet vite hvilken flate det er snakk om. Vi kan ikke lagre informasjon om flaten i objektet, for vi må jo kunne beregne dette for mange forskjellige flater, ja, for hvilken som helst flate, faktisk.

Som klient sender vi meldingen get_meters() (finnAntMeter() i figuren) til Covering-objektet. Sammen med meldingen sender vi opplysninger om flaten. Dette blir argument til funksjonen. Vi kan enten sende bredde og lengde som to tall, eller vi kan sende inn flate-objektet. Vi velger her å sende inn flate-objektet. Da ser prototypen slik ut:

//
// covering.hpp
//

#pragma once

#include "surface.hpp"
#include <string>

using namespace std;

const double grense = 0.02; // grense for å beregne en bredde ekstra

class Covering {
public:
  Covering(string name_, double price_, double width_);
  string get_name() const { return name; }
  double get_price() const { return price; }
  double get_width() const { return width; }

  /*
  * Skal beregne antall meter som trengs til en flate.
  * Teppet legges alltid på tvers av golvets lengde.
  * For å finne ut om det er billigere å legge teppet andre veien
  * må klienten bytte om lengde og bredde i den flaten som
  * sendes inn som argument.
  */
  double get_meters(const Surface &surface) const;
  double get_price(const Surface &surface) const;

private:
  string name;  // identifiserer belegget
  double price; // pris meter belegg (i lengden)
  double width; // meter
};

Merk spesielt const Surface &surface i :

double get_meters(const Surface &surface) const;

Her er parameteren Surface en const-referanse som muliggjør både:

double meters = covering.get_meters(Flate("Berits golv", 5, 6));

og

Surface surface("Berits golv", 5, 6);
double meters = covering.get_meters(surface);

I C++ dokumentasjon ser en ofte disse to begrepene:

  • r-value - verdi/objekt som ikke har en minneadresse
  • l-value - verdi/objekt som har en minneadresse

Surface("Berits golv", 5, 6) er en konstant (r-value). Uten const i const Surface &surface kan en bare bruke et objekt som er lagret i en variabel (l-value) som parameter til get_meters:

Surface surface("Berits golv", 5, 6);
double meters = belegget.get_meters(surface);

Implementasjonen ser slik ut:

//
// covering.hpp
//

#include "covering.hpp"
#include "surface.hpp"
#include <string>

using namespace std;

Covering::Covering(string name_, double price_, double width_)
    : name(name_), price(price_), width(width_) {}

double Covering::get_meters(const Surface &surface) const {
  double surface_length = surface.get_length();
  double surface_width = surface.get_width();

  int antBredder = surface_length / width;
  double rest = surface_length - antBredder * width;
  if (rest >= grense)
    antBredder++;
  return antBredder * surface_width;
}

double Covering::get_price(const Surface &surface) const {
  return get_meters(surface) * price;
}

En meget enkel testklient kan se slik ut:

//
// covering_test.cpp
//

#include "covering.hpp"
#include "surface.hpp"
#include <iostream>
#include <string>

using namespace std;
int main() {
  Surface surface("Berits golv", 5, 6);
  Covering covering("Vegg-til-vegg teppe", 243.50, 5);
  double meters = covering.get_meters(surface);
  double price = covering.get_price(surface);
  cout << "Du trenger " << meters << " meter, pris kr. " << price << endl;
}

/* Utskrift:
Du trenger 6 meter, pris kr. 1461
*/

Arv

Vi tar utgangspunkt i klassene vist i figuren nedenfor. Vi ser at disse tre klassene har en del felles. Alle sammen har navn og pris som attributter, samt operasjonene finnNavn, skrivUt og finnPrisPrM/-Liter/-Rull. De tre siste gir vi et felles navn: finnPrisPrEnhet.

I neste figur har vi samlet det som er felles for de tre klassene i klassen Materiale. Vi sier at klassen Materiale (basisklassen) representerer en generalisering av klassene Belegg, Maling og Tapet (subklasser). På den annen side er klassene Belegg, Maling og Tapet spesialiseringer av klassen Materiale.

Operasjonen skrivUt finner vi i alle fire klassene. Årsaken til dette er at implementasjonen av denne operasjonen er forskjellig for alle klassene.

Generalisering uttrykker alltid et "er"-forhold. Av figuren over leser vi dermed følgende i pilens retning:

  • Et belegg er et materiale
  • En maling er et materiale
  • En tapet er et materiale

Vi kan også, som nevnt tidligere, se på de objektene som en subklasse beskriver som en delmengde av de objektene basisklassen beskriver:

  • Alle belegg utgjør en delmengde av alle materialer
  • Alle malinger utgjør en delmengde av alle materialer
  • Alle tapeter utgjør en delmengde av alle materialer

Merk 1

Dersom vi ikke kan si at et objekt av en subklasse også er et objekt av basisklassen, har vi sannsynligvis ikke en ekte generalisering, og vi bør i stedet modellere sammenhengen mellom klassene på en annen måte.

Merk 2

Forveksle ikke aggregering med generalisering/spesialisering!

En aggregering mellom to klasser betyr at det eksisterer en forbindelse mellom objektene i de to klassene. Et objekt av den ene klassen består av et eller flere objekter av den andre klassen.

Generalisering/spesialisering uttrykker ikke et forhold mellom objekter av de involverte klassene, men mellom klassene (objektbeskrivelsene) som sådanne. Objektene som beskrives av en spesialisert klasse utgjør en delmengde av objektene som beskrives av den generelle klassen.

Å programmere et klassetre

Vi skal se hvordan vi programmerer klassetreet vist i den forrige figuren. La oss begynne øverst. Klassen Materiale er deklarert som følger:

#include <string>

class Material {
public:
  Material(const std::string &name_, double price_);
  const std::string &get_name() const { return name; }
  double get_price() const { return price; }
  void print() const;

private:
  std::string name; // identifiserer materialet
  double price;     // pris pr enhet
};

Ikke mye spesielt her. Og det er ikke å forvente heller. For det er slik at det alltid skal være mulig å lage en subklasse til en eksisterende klasse. En klasse kjenner ikke til sine subklasser. Derimot må en subklasse alltid kjenne til hvilken (eller "hvilke". I C++ kan en klasse ha mer enn en basisklasse. Dette kalles multippel arv) klasse den er subklasse til.

Vi forventer derfor at klassen Covering skiller seg litt fra det vi er vant med:

class Covering : public Material {
public:
  Covering(const std::string &name_, double price_, double width_);
  double get_width() const { return width; }
  void print() const;

private:
  double width; // meter
};

Vel, det var ikke mye. Men, altså, etter klassenavnet finner vi : public Material. Her forteller vi at klassen Covering er en subklasse til klassen Material (Det står public, det vil det nesten alltid gjøre).

En subklasse arver data- og funksjonsmedlemmer fra basisklassen (Merk forskjellen i begrepsbruk fra Java der private medlemmer ikke arves, men eventuelle data blir likevel en del av objektet). Når vi programmerer subklassen, programmerer vi bare det som skiller den fra basisklassen.

Implementasjonen til de to klassene er som følger. De ulike delene av implementasjonen gjennomgås lenger ut i denne leksjonen.

#include <iostream>

using namespace std;

Material::Material(const string &name_, double price_) : name(name_), price(price_) {}

void Material::print() const {
  cout << endl
       << "Navn:          " << name << endl
       << "Pris pr enhet  " << price << endl;
}

Covering::Covering(const string &name_, double price_, double width_)
    : Material(name_, price_),
      width(width_) {}

void Covering::print() const {
  Material::print();
  cout << "For belegg: " << endl
       << "Bredde:         : " << width << endl;
}

Legg merke til implementasjonen av Covering::print() der vi først kaller Material::print(). Vi må her kvalifisere navnet (Material::). Dersom vi ikke gjør det, vil funksjonen kalle seg selv. Kvalifisering er nødvendig dersom vi skal referere til et arvet navn, som er identisk med et navn som også er deklarert i klassen.

Se også implementasjonen av konstruktøren til klassen Covering (Covering::Covering). Konstruktører arves ikke, men vi bruker her konstruktøren til klassen Material, og deretter initialiserer datamedlemmet width som Covering har i tillegg.

Her er et lite program som prøver klassen Covering:

int main() {
  Covering covering("Super Duper Dux", 433.50, 4);
  // get_name() og get_price() arves til subklassene:
  cout << "Navn: " << covering.get_name() << ", pris: "
                   << covering.get_price() << endl;
  // Objektet bruker sin egen print()-funksjon (og ikke den som er arvet)
  belegget.print();

Det reserverte ordet protected

protected brukes på samme måte som private og public. Datamedlemmer med protected foran seg er kun tilgjengelig i subklasser.

La oss se på eksemplet foran. Vi ønsker nok ikke at klienter skal lage objekter av klassen Material, vi vil at de skal bestemme seg for hvilken type materiale de har foran seg. Vi kan få til dette ved å sette konstruktøren privat, men det er jo litt dumt her, for subklasser må jo kunne få tilgang til konstruktøren. Løsningen er å lage konstruktøren protected. Videre vil vi heller ikke at klienter skal bruke funksjonen print() som fins i klassen Material. (Hva i all verden skulle de bruke den til, og hvordan skulle de få til å bruke den, dersom de ikke kan lage objekter av klassen?)

Vi gjør altså konstruktøren og print() i klassen Material protected:

class Material {
public:
  const string &get_name() const { return name; }
  double get_price() const { return price; }
protected:
  Material(const string &name_, double price_);
  void print() const;
private:
  string name;  // identifiserer materialet
  double price; // pris pr enhet
};
